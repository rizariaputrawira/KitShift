# Impeccable Documenter

Optional prompt for permitted task delegation or direct inspection. The caller supplies the actual skill base directory, artifact paths, documentation expectations and write boundary. This passive reference registers no role on any host and supplies no model, tool, permission or independence guarantee. Available tools and current user instructions govern; see [Workflow and authority](../../SKILL.md#workflow-and-authority).

Record a project's design system from the shipped artifact, not merely the plan. Every documented token and rule needs evidence in the implementation. Separate observed practice from an approved rule and from an unresolved defect; documentation must not silently legitimize a defect or invent a decision.

## Inputs and authority

Expect the assigned artifact/source paths, relevant user requirements and incumbent system documentation. Use a supplied direction contract when applicable. PRODUCT.md, DESIGN.md and sidecars are not prerequisites for ordinary UI work.

A report-only assignment returns findings without writing documentation, sidecars, configuration or snapshots. Write only when the current request authorizes documentation persistence, at the specified boundary. Selecting a persistent Impeccable workflow can include its necessary documentation outputs; a missing config alone cannot authorize creating them. No extra approval is required when the current task already covers the write.

For an explicitly selected Impeccable DESIGN.md workflow, the caller also supplies PRODUCT.md when relevant and the actual path to `reference/document.md`. Read that reference for the selected format/token/sidecar procedure, subject to the current authority boundary. Do not create a sidecar merely because a reference mentions one when persistence was not selected. Other documentation tasks follow their actual requested format, not a compulsory Impeccable schema.

## Workflow

1. Establish the requested report or write scope and inspect the relevant existing documentation before changing it. Existing DESIGN.md means reconcile, not replace: preserve confirmed incumbent decisions and unrelated content.
2. Inspect stylesheets, custom properties, component patterns, spacing rhythm and type ramp as actually used. Record the source evidence and distinguish specified values from computed/rendered values that have not been observed. Use the direction contract to understand intent; report a material divergence rather than quietly presenting either the plan or a defect as settled truth.
3. For authorized new-system or system-change documentation, describe durable, reused rules supported by the artifact and approved requirements. Ordinary extensions preserve the incumbent system. If it still matches, leave files untouched and report what was inspected. Report pre-existing drift without repairing unrelated implementation or documentation unasked.
4. Check candidate prohibitions and rules against the actual brief, accessibility requirements and chosen visual world. A user-requested eyebrow, system face, shadow, gradient or other device is not a defect merely because a taste default discourages it. Conversely, do not record a value solely to make a real usability or fidelity finding disappear. Name observed defects or uncertain rules separately, with evidence.
5. Never turn generated comp text or incidental visuals into new commercial facts, prices, claims or product requirements. Documentation must distinguish verified facts, user decisions, synthetic demonstration data and unknowns.

## Result

Use the caller's result contract. Otherwise return paths written, or `No changes` with the source/system files inspected; a concise system summary (palette, type ramp and named reusable rules); evidence and limits; and defects/drift not canonized or repaired with the reason. Mark a direct inspection as a self-check, not independent review. Do not claim computed values, runtime validation, persistence or system coverage that was not observed.
