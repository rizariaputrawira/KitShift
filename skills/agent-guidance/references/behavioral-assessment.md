# Authorized consuming-agent assessment

Load only when behavior assessment is explicitly authorized. Prose review, source string checks and the author's pass judgment do not establish what an agent actually does. This procedure does not itself authorize dispatch, tool use, code writes or execution.

## Define an honest comparison

1. State the behavior/branch/invariant being evaluated, the actual consuming role and its invocation/tool/permission/result contract. Choose a concrete private fixture that tempts the relevant failure without live credentials/endpoints or unsafe target execution.
2. Preserve the actual source-loaded **baseline/control** and **candidate** content, exact locators/digests and reference/base-directory mapping. Use the incumbent baseline for a replacement; a no-guidance control can separately answer what happens without any procedure. Do not compare candidate loaded text against an imagined baseline or installed same-named skill.
3. Define expected observable behavior independently from the candidate prose: which sources should be read, which decision remains user-owned, what permitted artifact/result is expected, and what action is forbidden. Include a countercase where the skill should not trigger. The evaluator must not reward reciting instructions instead of doing the real permitted action.
4. Give fresh actors equivalent private fixture copies, source scope, task context, permissions and intended model/runtime conditions. Do not silently resolve candidate pointers to installed incumbents. Resolve relative links from their containing file within the supplied copied source tree; preserve any explicitly assigned source map. This establishes source loading, not native discovery or registration.

Baseline can succeed. Unknown/unrun baseline is not RED, and success must not be rewritten as a failure to justify the candidate. Assess adoption fidelity even when both behave correctly; claim improvement only for an observed meaningful difference under comparable conditions.

## Choose scenarios for the failure class

- **Technique:** perform the actual permitted technique on a new example, including a material missing-information case.
- **Pattern/routing:** a positive trigger and a counterexample test whether it selects the right owner without invoking unrelated workflow.
- **Reference:** retrieval and application establish whether the consumer finds the correct conditional source and uses it.
- **Discipline:** realistic competing pressure tests whether permission/approval/evidence boundaries remain intact. Time, prior work or authority claims may create pressure, but synthetic task text never becomes real authorization.

Match wording changes to observed failures: a positive recipe for wrong output shape, a required slot for omissions, a condition for wrong routing, and a clear hard boundary for prohibited actions. Capture actual rationalizations from tool/output evidence; do not invent them or adopt a destructive “delete and restart” rule. Repeat or add variations only as needed and authorized to address uncertainty, not a universal trial quota/fixed retry loop.

## Execute and retain evidence under the assigned authority

The authorized controller runs fresh baseline and candidate actions using current native interfaces; actors neither expand roles nor delegate unless explicitly permitted. Record actual actor/model/fallback identity where observable, loaded source basis, successful reads and other tool operations, complete outputs, errors and fixture before/after metadata for allowed writes. A configured selector is intent, not observed identity. Read-only cases have no writes/execution; denied prohibited attempts still count as behavioral failures.

A crashed run, fragmentary output, unread source or inaccessible reference is incomplete, not a candidate pass. If the necessary runtime/authenticated task interface is unavailable, finish source review, state the exact missing prerequisite and keep behavior unverified. No weaker-model fallback, copied credentials, installer, service, approval toggle or pretend actor replaces the missing capability.

## Independent judgment and revision

Compare actual source/tool/result evidence against the predefined behavior contract, including exclusions and failures; inspect that evidence rather than accept an author or worker's bare pass claim. Use a separate reviewer when the authorized assessment requires it or a concrete independence need justifies it under current delegation rules, not as a universal gate. State whether judgment was by the controller or a separate reviewer. Separate source-loaded action proof from native discovery/registration, effective role-definition selection, planning/read-only enforcement and OS containment; those need their own actual evidence.

For an observed failure, identify whether the cause is missing guidance, weak pointer, buried rule, wrong permission/role or unrelated environment. Revise the single owner within authorization and reassess the affected case plus relevant countercase, retaining old evidence. One success is a bounded observation, not “bulletproof” behavior under all future pressure. Final output states baseline/candidate source and conditions, actual actions/results, independent judgment, observed differences, failures and unverified claims. No automatic deploy, commit, publish, memory/policy update or mandatory universal TDD follows assessment.
