# Stitch Design Input Example: Taste Standard

> This bundled file is an illustrative, Stitch-specific input example, not canonical `DESIGN.md`, project documentation, or evidence about an existing project's design. Adapt or replace it only from the actual brief and observed project context. Existing project owners, tokens, accessibility needs, and requested scope take precedence.

## 1. Visual intent

Example direction only: restrained, gallery-like composition with clear hierarchy. Use this direction only if it fits the actual brief and product. Do not inherit the sample density, asymmetry, or motion level as project requirements.

## 2. Color and typography

The values below are sample values, not defaults or requirements. Replace them with observed project tokens when appropriate, or with brief-led proposals explicitly labeled as such.

- Canvas example: `#F9FAFB`
- Surface example: `#FFFFFF`
- Text example: `#18181B`
- Secondary text example: `#71717A`
- Accent examples: emerald `#10B981`, blue `#3B82F6`, rose `#E11D48`, amber `#F59E0B`
- Typeface examples: use the project's actual typefaces; do not force a particular family or ban an incumbent family.

Check contrast and legibility in the actual context. Do not assume these sample values are accessible for every use.

## 3. Components and layout

Describe only components, content hierarchy, and layout relevant to the requested screens. Existing component patterns and design-system guidance are primary. Cards, grids, imagery, shadows, rounded corners, alignment, and density are choices, not mandatory treatments. Do not use the example's former fixed hero, card, or feature-grid prescriptions as rules.

## 4. Responsive behavior

Follow the actual project's supported viewports and responsive conventions. Prevent clipping, unintended horizontal overflow, and inaccessible controls; choose breakpoints and layout changes to suit the content rather than inheriting a fixed sample breakpoint or universal single-column rule. Verify relevant viewport behavior when a real implementation is in scope, and report what was and was not inspected.

## 5. Interaction and motion

Motion is optional and must serve a requested interaction or content purpose. Do not require perpetual loops, animated loaders, staggered entrance sequences, spring physics, or a particular animation engine. Preserve immediate interaction feedback and reduced-motion behavior when motion is present. This example does not establish that any project component currently animates.

## 6. Brief-led exclusions

Record exclusions only when required by the actual brief, product conventions, factual accuracy, or accessibility. Do not carry forward universal bans on colors, fonts, layout patterns, copy, or component styles from this example. Never fabricate project facts, content, data, or assets.
