# Animation opportunities

Independently authored procedure preserving the proposal capability, not copied legacy prose. Read [principles](principles.md). This branch is inspection/report only: no source, harness, plan-directory, dependency, worktree or configuration writes.

## Gate

Evaluate each real candidate in order:

1. Frequency: frequent navigation/actions favor little or no movement; occasional panels and rare completion states may benefit. Keyboard activation alone does not decide the result. Do not delay actions or focus.
2. Purpose: name feedback, spatial consistency, state indication, preventing abrupt change, explanation, or rare delight. Reject decoration with no task value.
3. Speed: use compatible project tokens. Fallback ordinary UI timings usually stay under 300ms; a 200–500ms drawer needs a task-specific spatial/gesture reason. Reject a proposal requiring showy delay to work.
4. Function: preserve readable, actionable data and immediate controls. Check reduced/no-motion and pointer alternatives before recommending.

## Sweep

Inspect stack, accessible primitives, motion tokens, constraints and product context. Map actual frequency rather than treating guesses as measurements. Within the requested surface, consider:

- Missing action feedback, including non-motion states.
- Content swaps, expand/collapse, additions/removals and abrupt completion states.
- Trigger-connected panels and coherent dismissal paths.
- Occasional group entrances, only if they clarify sequence without blocking interaction.
- Gesture interruption, boundary resistance, velocity and pointer behavior.
- Rare first-run, empty or success moments where restrained delight serves the brief.

Use available symbol-aware tools for relationships and text search for structural discovery. Record actual file/line evidence or clear a category as absent/out of scope. Existing motion defects belong to [existing-motion audit/plan](existing-motion.md) or explicitly requested [diff review](diff-review.md), not an additive wishlist.

## Report

Prioritize a small set, usually at most 5–7 for a whole app and fewer for a view. Respect the user's output format.

| Location | Current state | Purpose | Frequency | Proposal |
|---|---|---|---|---|

For each surviving proposal supply grounded properties, project curve/duration or spring, reduced/no-motion alternative and pointer handling if relevant. Label unknown frequency and unobserved feel. Prefer transform/opacity; justify height/clipping exceptions and their verification costs.

Also report actual rejected candidates and the gate that rejected them. Do not invent 2–5 findings to fill a quota. Frequent command activation delaying focus and decorative movement of readable chart data are examples of reasons for rejection, not assumed fixture findings.

Finish with a short verdict on how much motion is warranted and the highest-leverage proposal. No surviving opportunities is a valid outcome. Suggestions-only requests remain read-only. If the current request also authorizes a specific plan or implementation, continue within that stated scope through the [existing-motion procedure](existing-motion.md) or [construction procedure](build.md), respectively; otherwise obtain the missing request before switching branches. An already authorized combined request needs neither a second confirmation nor an exact mode-name invocation.
