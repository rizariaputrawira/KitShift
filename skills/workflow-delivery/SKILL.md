# Project Delivery

Apply only when the user explicitly selects documentation-first delivery or an established project requirement calls for it, including authorized continuation of that workflow. Record that selection or requirement before imposing its baseline. A new app, substantial feature, ordinary continuation or context retrieval alone does not opt in. Otherwise use proportionate host planning, implementation, verification and necessary documentation without this workflow's pre-code gate.

Accept an explicit goal with existing artifact paths, or `resume [handoff-path]`. Loading this procedure is not execution authorization. Match documentation and review depth to the real boundary; a small change does not need a full-app pipeline. Use current host permissions, tools and approval rather than introducing an engine or another approval ritual.

## Establish the current boundary

1. Read applicable project instructions, supplied facts and existing requirement/design/plan owners. Preserve unrelated user changes. Establish the documentation-first selection or project requirement, then load [documentation baseline](references/documentation-baseline.md) for that boundary. Check `docs-engineering` is separately enabled and available before loading its baseline-selection/context capability. Never file-load or set up a disabled/unavailable dependency: report the affected explicitly requested documentation-first result as incomplete, while ordinary native work remains permitted. Safe provisional inspection can proceed without a manifest.
2. For `resume`, load [resumption](references/resumption.md) before dependent work. A read/load-only handoff request belongs to [workflow-handoff-read](../workflow-handoff-read/SKILL.md), not this execution branch.
3. Separate already observed acceptance, partial implementation, remaining acceptance and missing evidence. Do not replay completed stages simply because this is a fresh session. Missing material context or authorization blocks its dependent mutation, not unrelated safe inspection.

## Delivery procedure

1. **Specify the outcome.** Load [specification](references/specification.md). Synthesize supplied facts and inspected sources; do not re-interview for known answers. Use [workflow-brainstorming](../workflow-brainstorming/SKILL.md) only for unresolved consequential behavior. Extend the existing canonical product/requirement/design owner. For adopted projects resolve exact destinations through [docs-engineering locations](../docs-engineering/references/locations.md) and the manifest; before adoption respect existing owners without implicit migration. Do not establish a competing spec owner. In a host read-only planning mode keep checkout files read-only and return proposed content through its allowed channel.
   **Exit:** observable acceptance, constraints, boundaries/errors and non-goals are explicit; consequential choices have actual authorization, not a draft's “approved” label.
2. **Resolve UI evidence only when affected.** Follow applicable current project instructions and the relevant enabled UI skill through current native interfaces. Start with the approved project design and actual incumbent states; account for relevant empty/loading/error, accessibility and narrow/wide behavior. OpenDesign generation/refinement is a prerequisite only when the user or established project contract specifically requires it. Record that exact requirement before treating unavailable service access as a blocker. Do not demand MCP credentials or a new external artifact for ordinary authorized in-place UI work. A material scope-changing design requires resolution through current native authorization before dependent work.
   **Exit:** required UI baseline evidence is sufficient for the selected delivery boundary. An unresolved required UI baseline blocks production implementation of that boundary, not safe inspection or authorized document/design work. Unrelated ordinary native tasks remain permitted.
3. **Prepare and review the selected baseline, then plan delivery.** Follow [documentation baseline](references/documentation-baseline.md) in information-prerequisite order for this opted-in boundary. Load [planning](references/planning.md). Tie every material criterion to a complete vertical slice and observable proof; include interfaces, prerequisites, errors and irreversible choices. Prepare required baseline information before app implementation. For consequential multi-slice work load [docs-plan-review](../docs-plan-review/SKILL.md); review directly or delegate useful bounded source inspection under current host rules, without a mandatory independent worker. Review baseline and plan together when host approval is required, without another approval ritual. Keep the operative plan accessible; persist a repository mirror only for an authorized project, team or portability need. Persist necessary reviewed baseline content within current authority before code. A mirror is not approval.
   **Exit:** every selected required pre-code owner is substantive, consistent and reviewed; full acceptance is planned, dependencies feasible, and current authorization covers the material baseline decisions and implementation scope.
   **Execution choice:** use available execution and delegation modes according to the task, actual host capabilities and current permissions. Optional execution modes may be used when supported and useful; they impose no model mapping, consultation boundary or mandatory worker. For a transition, carry the operative plan, authorization basis, completed evidence and remaining dependencies forward; mode activation is not approval and does not require replaying preparation.
4. **Implement the next authorized slice.** Read its plan, reviewed baseline anchors and affected code/tests; preserve useful real partial progress. Use [implementation brief](references/implementation-brief.md) when dispatching through actual available host task interfaces; delegation is optional and cannot bypass readiness. One integration owner controls shared writes and final checks. Workers do not run verification unless explicitly assigned. Use [code-tdd](../code-tdd/SKILL.md) only for requested/approved test-first, [code-debugging](../code-debugging/SKILL.md) for difficult diagnosis and [code-review](../code-review/SKILL.md) for requested/consequential correctness/spec review. Focused security and explicit audits load their distinct owners, not a universal audit. Load [review feedback](references/review-feedback.md) when findings arrive. Material changes to reviewed requirements, architecture/interfaces, security/platform rules or scope follow [changes during implementation](references/documentation-baseline.md#changes-during-implementation): update intended owners/plan and obtain host reapproval before dependent code. Corrections within unchanged intent may use current scope.
   **Exit:** the complete slice and all affected callers/docs/tests are implemented within the authorized boundary; actual evidence, gaps and feedback dispositions are recorded.
5. **Prove acceptance and reconcile every affected document.** Load [verification](references/verification.md) and [as-built reconciliation](references/documentation-baseline.md#as-built-reconciliation). The integration owner assesses the complete boundary after workers land through authorized actual checks. Incomplete reports or source shape cannot satisfy behavioral acceptance. Record failures/unrun checks. Inspect and reconcile all affected selected product/requirement, architecture/ADR, design/contract, data/security/platform, verification/trace, release/configuration/recovery/operations and user owners as applicable, not only the app guide. Create a guide only for an unmet real reader need. Do not label proposed behavior shipped.
   **Exit:** every required criterion has relevant observed evidence, end-to-end consumers work, and all affected canonical owners/links/states accurately describe the verified result and unresolved limits.

## Reporting and interruption

Return the acceptance-to-evidence result, actual changes, observed checks/outcomes and unresolved blockers; distinguish source inspection from exercised behavior. Retain relevant unchanged observed evidence without gratuitous replay, but invalidate it when its material basis changes. Explicit pause/export uses [workflow-handoff](../workflow-handoff/SKILL.md); requested learning extraction uses [workflow-retrospective](../workflow-retrospective/SKILL.md). No automatic commits, worktrees, tracker publishing, job restarts, new state database or provider/model changes.
