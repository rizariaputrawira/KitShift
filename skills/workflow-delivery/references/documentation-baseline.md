# Documentation-first delivery baseline

## Applicability and authority

Apply this pre-code baseline only when the user explicitly selects documentation-first delivery or an established project requirement calls for it, including authorized continuation of that selected boundary. Record the selection or requirement. A new app or substantial feature alone does not activate it; otherwise use proportionate host planning and necessary documentation. Once selected, the baseline covers the complete authorized delivery boundary, not merely its first tracer or worker slice. Do not silently reduce that boundary to evade required information.

This is an opt-in local delivery policy, not a host requirement, ISO-prescribed waterfall, formal conformity or runtime enforcement. Loading a skill, completing review or writing `approved` grants no execution permission. Current host permissions and user authorization still bind the material content, plan and scope; no special approval receipt format is required unless the project requires one.

Host read-only planning modes do not write checkout documents or code. Propose substantive baseline content through the allowed session-local/planning channel. After current authorization, persist the exact necessary reviewed baseline content before app code. Material post-approval document/design decisions require host reapproval before dependent implementation, not a hidden second approval system. One host approval may cover the exact reviewed baseline and implementation plan together.

Before readiness, allow source inspection and authorized document/design-artifact work only for this delivery. Do not retain app source, tests, scaffolding or runtime-configuration changes, install app dependencies, migrate the app or start app services. Document work grants no implicit tool setup, download or service permission. Preserve real pre-existing work. Do not block unrelated ordinary work or reactivate a disabled/unavailable suite. An explicitly requested documentation-first delivery with missing procedure/material sources remains incomplete until those inputs or a revised user scope are available.

## Select and prepare the baseline

Check the separately enabled docs-engineering capability is available before reading it. Use [profiles](../../docs-engineering/references/profiles.md), [manifest](../../docs-engineering/references/manifest.md) and [locations](../../docs-engineering/references/locations.md) for profiles, manifest v1 and canonical resolution, then their relevant catalog/owner-checklist pointers. Select/document the baseline for this complete scope. For already adopted projects use the canonical manifest/navigator and exact catalog resolver; do not substitute another index.

Before adoption a sufficient existing index/manifest may support provisional or existing delivery context when it records owner/anchor, applicability/omission, prerequisites, review and source basis. Do not reorganize it merely for delivery. When the authorized baseline workflow explicitly includes docs-engineering setup/adoption, follow that owner's normalization and mandatory navigator/manifest contract. Otherwise propose adoption if needed, without silently migrating or claiming the standard was adopted. Invalid, unreadable, unsupported or ownership-ambiguous manifests require scoped authorized resolution, never bypass with another index.

These ordered stages require logical information coverage, not separate files. In adopted projects combine genuinely shared ownership at canonical owner anchors with reasons; new standalone artifacts resolve their exact catalog destinations. Before adoption retain sufficient existing sources. Never infer a family-derived fallback or create a competing documentation hierarchy.

| 3 | Architecture boundaries/responsibilities, data/trust flows, external contracts, threats/control allocation and accepted consequential decisions | `architecture-description`, selected views, actual-interface `openapi`/`asyncapi`, applicable `threat-model`/`security-controls`; docs-domain-modeling for glossary/ADRs | Requirements allocated to coherent intended architecture/controls; actual prerequisites and unresolved decisions explicit |
| 4 | Detailed data/state/error/concurrency/dependency/integration/platform choices and relevant UI behavior/design | `technical-design` (TSD/TDD/SDD aliases), canonical formal contracts and security design; applicable current project UI guidance and enabled UI skills | Implementation-relevant interfaces/invariants and ownership sufficiently specified; visual evidence accessible when the user or established project contract requires it. Start security classification/requirements at stages 0/2, not a late security phase. Independent requirement/test-strategy sections can be drafted after stable purpose inputs; independent design/release/user sections after sufficient relevant architecture inputs. Review consumed prerequisites before downstream commitment. Numeric catalog phases are not execution order: verification reports and user/release plans have different planned versus observed content.

Retain the four profiles. Choose lean only from inspected genuinely low-complexity/risk scope; standard for ordinary substantial production applications; controlled for actual named signoff/baseline/full-trace obligations; regulated only for identified regulatory obligations. Types alone do not imply regulation. Lean reduces file count/detail, not necessary behavior/design/security/proof coverage. Existing suitable project rigor governs. Inline links can provide lean trace; explicit maps remain where current risk/rigor calls for them. Pre-code trace allocates requirements to architecture/design and planned test sources, never invented implementation nodes, timestamps or passed evidence.

## Environment preflight

The main/integration owner follows this procedure when a selected delivery action or its planned proof depends on environment capabilities.

1. **Bind prerequisites to consumers.** Read the current authorized boundary and maintained requirements/design/plan owners. Identify only actual prerequisites for the selected implementation action, setup/startup path or acceptance proof: declared runtime/version, necessary tools, services/integrations, output/store paths and non-secret authentication/permission status. Name the consuming action or criterion, its source and when the capability is needed. An optional improvement, installed integration, missing unused MCP or another project's stack is not automatically required. Do not sweep the machine or invent prerequisites. Resolve an unsettled material requirement/design decision through this baseline's existing readiness rule; do not choose a different platform or substitute a tool to make preflight green.
2. **Inspect the owning interface first.** Inspect supplied paths, the selected host's actually exposed tools and relevant non-secret configuration/status. Add or update prerequisite-specific rows in the existing plan/review record under its five columns: `Information/criterion | Canonical owner/anchor | Source basis and prerequisite sufficiency | Review/disposition and gap | Evidence due now or later`. Record the observed fact and its scope, exact safe command/path/interface if used, result or limitation, affected action/proof and required next action. Do not create a new file, manifest field, status enum or task database. Use [verification's result contract](verification.md#result-contract) for acceptance, not competing acceptance states.
3. **Apply inspection-first authority.** A known safe local version/status command is permitted only when current native/user permissions allow execution and its behavior is understood. Inspect a project script before considering execution; a name such as `check` or `status` is not proof that it is passive. Do not invoke dependency/package runners, installers, activation scripts or app startup merely to discover availability. Active service/auth requests or temporary create/delete writability probes require explicit existing authority for those operations and, where applicable, completed baseline readiness. Without those conditions, do not attempt the probe; record the affected capability as unverified. Under a host/assignment read-only boundary that forbids execution or writes, propose observations/checks only through the allowed channel.
4. **Keep evidence claims narrow.** A configured endpoint is not a successful connection. Tool discovery or an executable's presence is not proof that the app starts. A successful version command establishes that executable/version observation, not every feature or dependency. Credential-presence/configuration signals do not establish valid authentication or permission for a particular action. Directory existence, mode bits or an access check do not prove that an actual write will succeed. Do not read `.env` or credential stores, dump environment/configuration, retrieve tokens or expose private auth parameters for this preflight. Without a safe non-secret status interface, leave the needed auth fact unverified; request only the necessary non-secret action/input when the dependent action is actually ready.
5. **Hold only dependent work and carry observations forward.** Hold an action/proof when it requires a prerequisite that is confirmed missing or remains unverified; unverified is neither absent nor ready. Optional/unrelated gaps do not hold delivery. Continue independent authorized work without claiming the complete outcome when required proof remains missing. Missing execution/verification capacity alone does not make otherwise complete requirements/design information incomplete: retain the whole-boundary pre-code information gate, but do not add a global environment gate. Before resuming a blocked action, confirm that its prerequisite is satisfied. Reuse observations while their relevant source/environment/permission/requirement basis remains valid; recheck only materially affected observations. Environment access or availability never grants permission. A material change to reviewed platform, interface, security or scope follows [Changes during implementation](#changes-during-implementation) before dependent mutation.

Do not start services, change permissions/settings, install dependencies, switch provider/model/runtime, reactivate disabled capabilities or request approval for settled decisions to repair preflight. Existing user-authorized setup remains separate work under its own authority, not a side effect of inspection. No aggregate “environment healthy” verdict substitutes for criterion-level proof.

## Before-code readiness

Record a short inspection-backed table in the existing plan/review owner, not new manifest fields or a task database:

`Information/criterion | Canonical owner/anchor | Source basis and prerequisite sufficiency | Review/disposition and gap | Evidence due now or later`

Examine content, not filenames or statuses. Every selected required pre-code item needs one sufficient accessible owner, resolved material choices/conflicts, relevant source freshness, complete negative behavior, design/verification allocation and reviewed dispositions. Optional unrelated views may be omitted with rationale. Required unfinished architecture/contracts cannot be bypassed because a tracer is possible. Standards access limits alone do not defeat voluntary alignment; missing interpretation of an actual binding obligation blocks its dependent commitment.

Keep document knowledge validation, implementation acceptance and current permission separate. Review baseline and plan together through existing host approval when required. Review may be direct or use useful permitted delegation; consequential scope does not mandate an independent worker. Current authorization must cover material baseline decisions and implementation scope. Follow [authorization reconciliation](resumption.md#authorization-is-independently-verified) rather than requiring a special receipt. An unresolved material fact cannot be repaired with a marker; document-drafting authority is not production-code authority. Do not re-ask an exact decision already covered by current authority.

## Changes during implementation

Before changing a material requirement, architecture/interface, security/platform rule or approved scope, identify affected owners, update/propose intended content, resolve cross-owner conflicts and revise the plan. Obtain existing required native reapproval before dependent code. Use authorized `create`/owner-extension for changed intended design; `maintain` still distinguishes observed as-built facts. Corrections within unchanged reviewed intent may proceed under their existing scope. Invalidate only materially affected evidence. Never lower intended acceptance to agree with code. Reversible internal changes are still subject to this rule when they materially change reviewed intent.

## As-built reconciliation

After each material verified change and at final delivery, inspect every affected selected owner: product/requirements, architecture/ADRs, detailed design/native contracts, data/security/platform, verification/trace, release/configuration/migration/rollback, operations/recovery and user docs as applicable. Compare actual sources and relevant exercised evidence. Update accurate descriptive content, retain real unresolved acceptance/limits, and repair affected links/owner states only to supported levels.

Actual tests, review findings, releases, incidents, restore and store outcomes are recorded only after observation. Do not create fictional result logs or postmortems. Final app completion requires both every required criterion satisfied and complete affected-document reconciliation. Source-inspected as-built facts may be stated as such; missing required runtime/deployment evidence remains unverified. A guide update, code-complete slice or worker summary alone cannot establish full app completion.
