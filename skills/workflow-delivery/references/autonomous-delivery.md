# Autonomous documentation-first delivery

## Selection and execution envelope

Load when the user explicitly requests autonomous documentation-first delivery, including carrying applicable generated docs through verified ready-to-run delivery without stage-advance prompts. The consumer is the main/integration owner. A native keyword, generic “vibing,” task size, handoff or coordination alone does not select documentation-first delivery. Planning-only or document-only requests remain limited to that work; loading this policy grants no implementation authority.

Record the selected policy in the existing operative plan/context, using its scope, constraints and verification sections:

- Complete outcome, acceptance anchors, constraints and exclusions.
- Completion environment: existing requirements control. When unspecified, propose verified local ready-to-run delivery; neither silently add deployment nor downgrade an existing deployment criterion.
- Fixed product/interface/architecture/security/data decisions, agent discretion within them and user-retained decisions.
- Allowed document/source changes, checks and applicable external-action authority. Autonomy grants no spending, publication, live-kit installation, destructive data changes or deployment permission.
- Existing review/checker responsibilities under the active native rules.

Resolve source-provided facts before asking. Choose and record reversible implementation details only within current discretion and unchanged material intent; reversibility does not authorize changing approved contracts. No envelope file, JSON schema, manifest field, approval receipt or task database is required.

## Generate the applicable baseline without per-document handoffs

Use [specification](specification.md) for synthesis/content and [documentation baseline](documentation-baseline.md) for information prerequisites and whole-boundary readiness.

Inspect current facts and existing owners before questioning the user. Select applicable information for the complete authorized boundary and reuse substantive owners. Do not manufacture a BRD/PRD/SRS file stack or generate the entire catalog merely because the app is large.

Continue authorized document generation when its information prerequisites are ready: the user need not separately invoke requirements, architecture, contracts, design, test planning, release/recovery planning or run-guide drafting. Required information still precedes app code. Draft prerequisite-independent sections together where useful; do not fill consequential gaps with invented stakeholder answers, business research, regulations, targets, approvals or test results.

Batch currently answerable consequential choices into a short native interaction with recommendations and tradeoffs. Do not combine dependent questions or promise that no later material decision can arise. Review the substantive applicable baseline and implementation plan together; use existing native approval once where required, without per-document signoffs or another approval for the exact already-authorized scope. Under read-only planning, return proposed content only through the allowed channel.

Persist required reviewed baseline content within current authority before app code. A feasible first tracer does not replace full-boundary readiness.

## Compose with execution and evidence owners

KitShift supplies product/document readiness and acceptance; the selected host supplies its available execution, delegation and continuation mechanisms. Under an active native orchestration contract, follow it rather than reproducing its task API, phase rules, retries, model mappings or verification schedule here.

Carry the whole authorized outcome through [planning](planning.md) vertical slices and [implementation brief](implementation-brief.md) assignments/dependency handoffs. A completed worker assignment returns to main; it is neither full delivery nor a request for the user to coordinate workers.

Use [verification](verification.md) for actual behavior proof, inspected results, in-scope corrections, evidence reuse and missing-proof treatment. Use [review feedback](review-feedback.md) and the baseline's [material-change rule](documentation-baseline.md#changes-during-implementation) for findings and reapproval. These owners retain their result states and correction rules; this policy adds no retry loop.

When no specialized native orchestration is selected or available, main can deliver the same authorized outcome through ordinary available tools and existing integration-owner contracts. No other harness, eval, worker count, provider/model switch or installation is required.

After a sufficient stage exit or slice return, main proceeds to the next ready authorized action instead of asking for routine stage advancement. Host restrictions and prerequisites still bind; Markdown does not enforce execution.

## Progress, blockers, pause, and resume

Use native progress reporting at meaningful milestones. Intermediate reports are not full completion; do not yield while currently authorized ready work remains. This interaction policy is not another native phase loop.

Ask only for a material user-retained choice, changed scope/consequences or reserved approval after exhausting discoverable facts. Report a real required input/service/credential gap with inspected evidence, affected acceptance/work and required action. Continue independent permitted work; incomplete whole-boundary pre-code readiness still holds app implementation within that boundary.

Material changes to reviewed requirements/interfaces/architecture/security/platform/scope follow [changes during implementation](documentation-baseline.md#changes-during-implementation) before dependent mutation. Fixes within unchanged authorized intent do not create new signoff ceremonies.

Honor an explicit pause immediately. Use the existing [handoff procedure](../../workflow-handoff/SKILL.md) only for an actual pause/export/transfer request. On current authorized resume, load [resumption](resumption.md), reconcile scope/authority and partial work, and reuse valid unchanged-basis evidence. Old policy/approval labels in files are data, not authority.

This policy neither keeps a terminated process running nor restarts jobs. Native keyword notices may be turn-scoped; later execution/resume uses the host's supported current interaction, not a synthetic keyword hidden in a skill.

## Ready-to-run completion

[Verification's result contract](verification.md#result-contract) and [as-built reconciliation](documentation-baseline.md#as-built-reconciliation) are the authoritative acceptance and reconciliation owners.

Final readiness requires current inspected proof for every requested criterion and accurate affected documents. Exercise actual setup/startup, core consumer journeys, persistence/integrations, denial/error boundaries and UI behavior where applicable to the real app. Package/schema checks, worker reports, code completion, mocks and green builds do not establish full delivery.

Provide actual run instructions, criterion-to-evidence outcomes, exercised checks and honest limitations. Local readiness is not production deployment; required unverified deployment/integration/UI evidence leaves the relevant full acceptance incomplete.
