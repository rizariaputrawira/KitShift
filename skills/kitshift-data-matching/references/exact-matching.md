# Exact and normalized matching

Establish identifiers' namespace, time validity and semantic authority, coverage, allowed normalization and expected relationship before matching. Identify all components of composite keys and exclude records with any missing component from ordinary equality matching. Apply the source's explicit missing-token contract: a literal `NA` can be a real identifier. Empty normalized strings cannot be keys. Keep raw spellings, and enumerate distinct originals sharing normalized keys; collisions are issues, not proof of identity. Check per-side key multiplicity and conflicting reliable attributes before accepting pairs. A duplicate key or reused target violating the expected relationship is not resolved by selecting the first row.

For pandas, specify key columns explicitly, separate incomplete-key records before `merge`, and use `validate` for the declared relationship plus `indicator` to inspect provenance. pandas can match null keys to one another, unlike ordinary SQL equality. `validate='many_to_many'` performs no uniqueness checks: independently evaluate and justify actual multiplicities and expansion. A merge indicator alone does not decide entity identity. Record the actual pandas version and check the outputs and cardinality; these caveats are based on the pandas 2.3.3 [merge documentation](https://pandas.pydata.org/pandas-docs/version/2.3.3/reference/api/pandas.merge.html).
