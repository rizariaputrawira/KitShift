# Requirements and product behavior

## Business and product inputs
Brief/BRD captures justified business needs and outcomes, not system behavior. PRD owns product/user outcomes and acceptance intent. Identify stakeholders/concerns, scope/non-goals, assumptions with validation route, constraints with source authority, and risks with cause/event/consequence/owner/review trigger. Extend existing product sources when audience/lifecycle match; no automatic BRD+PRD. Review business facts against accountable source, product claims against supplied research/decisions; invented audiences, market facts or obligations remain unacceptable.

## Behavior and acceptance
SRS owns formal system behavior and usually functional requirements; stories/use cases/acceptance criteria are meaningful sections or distinct audience views, not competing owners. FSD is optional organization-specific functional detail and cross-links SRS instead of copying it. For each material requirement capture stable ID where risk/production warrants, source/need, scope, owner, rationale, conditions, observable outcome, failure/negative/boundary cases and update triggers. Requirements constrain design; do not prescribe implementation unless intentional and authorized. Use cases add actor, trigger, preconditions, normal/alternate/error transitions and postconditions. Stories add actor benefit and acceptance; unresolved negotiation is not approval.

Prefer stable category-number IDs and atomic, user-observable requirements. Keep existing IDs across wording/location changes; split a genuinely compound requirement into linked criteria rather than hide separate failure outcomes. Record explicit exclusions and rationale in the existing owner. Map each acceptance criterion to all relevant deliverables, integration boundaries and evidence: many-to-many mapping is valid, and unmapped criteria are real gaps. Do not assign one-phase ownership or mark execution checkboxes as requirement acceptance. Intent, approval, implementation and observed verification remain distinct states.

## Quality and security acceptance
NFR may be an SRS section. State metric, workload, environment, observation window, failure threshold and method only where known; unresolved target is not an invented number. Select performance, reliability, availability, interoperability, maintainability, usability/accessibility, safety/privacy/security from actual product risk/obligations. A security requirement names invariant, actors/assets/trust boundary and verification route. Lean does not waive risk. Approval/document review is distinct from implemented/runtime-verified. Verify scoped acceptance at the canonical source, report ambiguity/duplicate ownership/conflicts, and change only through authorized owner decisions.

## Trace and change
Use [traceability](traceability.md#coverage-and-evidence-decisions) for need/behavior/design/implementation/test/evidence chains. New behavior, changed failure boundaries, platform policy, threat context or accepted quality target triggers review of affected requirements, not all documents. Preserve unchanged user content and IDs. A task request alone does not supersede security requirements. Requirements approved before implementation can constrain work while runtime acceptance remains not-run.
