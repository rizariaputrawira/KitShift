# Mobile shared information and platform deltas

## Shared mobile requirements
One canonical shared owner governs common product behavior; Android/iOS deltas link to it, never copy it. Compose mobile-application and game with independent platform lists; no android-game/ios-game taxonomy. Lifecycle foreground/background/interruption/process-death/restoration acceptance; storage sensitivity/access/retention/deletion; offline queues/conflicts/idempotency/resync; notifications consent/preview/destination; deep links domain ownership/untrusted parameters/auth-gating; privacy data purposes/minimization/SDK flows; accessibility; OS/device support; verification/release are selected from actual features. Unknown product behavior remains an explicit gap.

Shared mobile storage requirements describe intent, `secure-storage` describes cross-system protection design, and platform mechanisms allocate it; these are not three copies of the same fact. Privacy requirements and actual disclosure records remain distinct. Changed lifecycle/storage/sync/link/notification/data behavior triggers review of affected shared owner and deltas.

## Android delta
Inspect actual manifest/merged components, target/min/support API and app build sources. Record each permission and feature rationale, denial/revocation behavior; exported component/intent trust, access protection and malicious-input acceptance; Android Keystore key purpose/custody/access and app/upload signing distinction; supported API/device scope; Play channel/policy/data-safety evidence. Do not document private keys, secrets or pretend a signing plan is a signed artifact. Platform tests cover relevant interruption, denial, exported entrypoints, link validation, storage and actual supported devices/APIs.

Official dated sources: [exported components](https://developer.android.com/privacy-and-security/risks/android-exported), [signing](https://developer.android.com/studio/publish/app-signing), [data use](https://developer.android.com/privacy-and-security/declare-data-use), [Play data-safety explanation](https://support.google.com/googleplay/answer/11416267). They are mutable and app-specific; inspect current linked developer submission policy for the actual release, not perpetual hard-coded API thresholds. App/SDK collection and sharing must agree with disclosures; a declaration does not establish privacy or approval.

## iOS delta
Inspect actual entitlements/capabilities and feature rationale, signed/provisioned entitlement consistency, consent/access boundaries; privacy declarations/manifests and required-reason API/SDK applicability; OS/device support; Keychain item type/accessibility/access groups/sharing, lifecycle and deletion; signing/certificate/provisioning/capability roles and App Store distribution. No credentials or signing keys in documentation. Test link/universal-link input/auth boundaries, entitlement access, permission denial, protected storage/restoration and supported OS/device behavior.

Official mutable sources: [entitlements](https://developer.apple.com/documentation/bundleresources/entitlements), [Keychain](https://developer.apple.com/documentation/security/keychain-services), [privacy manifests](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files), [App Review](https://developer.apple.com/app-store/review/guidelines), [privacy details](https://developer.apple.com/app-store/app-privacy-details/). Record policy/review date and app/SDK interpretation. Approval requires actual store result, not checklist completion.

## Mobile evidence and release
Declared support matrix and observed platform evidence are separate. A shared test with Android-only evidence cannot verify iOS-specific or cross-platform acceptance. Link shared requirement -> bounded deltas -> actual test/review evidence, with platform/basis/time/result/not-run. Maintain only affected deltas, keeping common source singular. Store/SDK/OS/policy/build/signing changes trigger applicable compatibility/privacy/release review. Missing real devices/services/toolchains blocks those execution claims, not documentation authoring.
